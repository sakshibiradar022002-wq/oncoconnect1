# VELTRUVIA Risk Register

Status of each risk is assessed against the code and infrastructure **as of
2026-10-05 (v2.5.0)**; verification evidence for O1, O5 and S1 was refreshed
on the live instance **2026-11-23 (v2.6.8)**. "Accepted" means an owner has
consciously accepted the residual risk; nothing is marked closed without
evidence.

Severity × Likelihood → Rating: **H** high, **M** medium, **L** low.

ZAP baseline against production 2026-11-23 (2.6.8) — **1 Medium / 1 Low / 5 Informational**, no blocking finding (`reports/zap/zap-baseline.{html,json}`, gitignored): Medium = CSP `style-src 'unsafe-inline'` on 4 responses, Low = Cross-Origin-Embedder-Policy missing/invalid on 2, info = suspicious comments (11, incl. `/js/actions.js`), modern-web-app, cache-control advice, and `appointments.ics` served non-storable. Full **active** scan against the demo build on `localhost:3124` (2026-11-24, unattended, ~41 min): **1 Medium / 1 Low / 5 Informational** — the Medium is the same CSP `style-src` allowance, the Low the same COEP header — and **120 other active rules PASS**, including SQL injection, XSS, SSRF, XXE, path traversal, command/template injection, LDAP and padding-oracle probes; no authentication bypass and no admin route reachable unauthenticated. Two of the warns are decisions to take, not defects: registration OTP reveals whether an account exists (`409` vs `200`), and TOTP enrolment needs no password re-entry. Remaining by hand: OTP replay/TTL, reset-token reuse, password-change revocation, TOTP replay — all need a mailbox or authenticator ([PENTEST-SCOPE.md](PENTEST-SCOPE.md) §4). **Open (automated coverage complete, four manual checks pending)**. Credentials that had been disclosed in plain text — Gmail, both app accounts (`admin@veltruvia.local`, doctor), the `ubuntu` and `root` passwords — were rotated 2026-11-23, app hashes rewritten in the app's own `pbkdf2$210000$…` format and re-verified by login; the dedicated automated-update SSH key was removed from `authorized_keys` and the stale `/root/veltruvia-admin-credentials.txt` deleted, so the admin-login smoke test no longer skips silently. |

## 3. Availability / operational risks

| ID | Risk | Sev | Lik | Rating | Mitigation in place | Residual / status |
|----|------|-----|-----|--------|------|------|
| O1 | Data loss (DB corruption, ransomware, accidental delete) | H | L | **M** | Nightly `VACUUM INTO` snapshot + tar (VM 02:15 UTC, keep 14); daily offsite pull to Sara's PC (keep 30); **freshness guard: pull exits 4 + watchdog Event ID 2 if newest offsite copy > 36 h old** (live-verified both branches); `scripts/offsite-backup.mjs` adds a second copy — AES-256-GCM, SHA-256 manifest, decrypt-verified before upload, timestamped retention to any path or rclone remote; its `--source` is the 02:15 timer's `~/veltruvia-backups/*.tar.gz`, not the `app/backups` restart snapshots; `--images <dir>` adds the imaging store (`data/images`), which the DB dump does not contain | Second copy needs a key (`openssl rand -hex 32`) and a remote configured once; whole-machine snapshots still share the AWS account/region. **Verified on production 2026-11-23**: the in-app scheduler writes a real snapshot 30 s after boot and every **6 h** (`backups/veltruvia-2026-11-23T11-02-31.db`, 1,163,264 B, `pragma quick_check` → `ok`, restored copy holds both users and 32 kv rows). The earlier silent failure — `VACUUM INTO` rejected under sql.js, copy fallback never reached, success logged anyway, no file written — is fixed and the fallback is now logged; every snapshot is header-validated before being reported. `--images` produced and decrypt-verified an 82 KB image archive, so the imaging store now has an off-box copy alongside the DB dump. Those off-box copies are ciphertext and the only key was `/home/ubuntu/.secrets/offsite.key` on the same VM, so instance loss would have left them unreadable; the key is now also held off-box (password manager, separate from the archives) and the transfer copy deleted 2026-11-23 — **mitigated**, with the caveat that key custody is manual and undocumented in code. |
| O2 | Service outage unnoticed | M | M | **M** | Uptime watchdog every 15 min → `watchdog.log` + Windows Event Log; `/health?deep=1` DB check; `scripts/uptime-heartbeat.mjs` is a dead-man's switch — cron pings an external check only while the service answers, so a dead VM also alerts | External dead-man's switch **live since 2026-11-23**: cron `*/5 * * * *` runs `scripts/uptime-heartbeat.mjs` with `HEARTBEAT_URL="$(cat ~/.secrets/healthchecks.url)"`; pings only while the service answers, so a dead VM goes silent and alerts. Confirmed by three consecutive `200`s. The check URL is kept outside the repo (`~/.secrets/`, not tracked); the Windows watchdog remains as a second, PC-side signal. |
| O3 | Single VM = single point of failure | H | M | **H** | Nightly offsite backups; restore procedure documented (`vm-restore-clean.sh`); RPO ≤ 24 h / RTO 4–8 h in SUPPORT-POLICY | No warm standby. Whole-machine snapshot + cutover path in [STANDBY-RUNBOOK.md](STANDBY-RUNBOOK.md); the snapshot add-on itself is **not yet enabled** (one AWS CLI command, §1). **Accepted** at current stage |
| O4 | TLS/certificate expiry takes site offline | H | L | **M** | Caddy auto-renewal; `check-cert.ps1`; cert-expiry in truth-check | Renewal depends on Caddy + DNS health — **mitigated** |
| O5 | Failed deploy bricks the service | M | L | **L** | Release checklist, `npm run precommit` (check+test+verify), SHA256SUMS, versioned bundles | No automated rollback job — restore-from-backup is the rollback. **Accepted**. Note from the 2026-11-23 deploy: `stage`/`swap` skip the admin-login smoke test when `/root/veltruvia-admin-credentials.txt` is missing or stale (it was, after a password reset), so a successful deploy can still leave sign-in unverified — log in once by hand after any swap. |
