Sign-in model

  • Doctors — register with email and password, then confirm the account with a six-digit code sent to that address (/api/auth/otp/send → /api/auth/otp/verify). Repeated failures lock the account briefly.
  • Labs — sign in with the credentials the clinic issues (/api/sync/lab-login).
  • Patients — sign in with their MRN and password (/api/sync/patient-login).
  • Sessions live in an HTTP-only cc_session cookie and are revoked on sign-out or by an administrator.

How sync works

The desktop apps keep working locally and push changes when a connection is available. Each role has its own scoped sync endpoint — /api/sync for doctors, /api/sync/patient and /api/sync/lab for the scoped apps — and the server merges by record id and updated timestamp. A patient entry logged offline appears in the doctor's dashboard once the phone reconnects.

Scope of the OpenAPI document. /api/docs/openapi.json describes the core surface only — System, Auth, Sync, Admin, Team, Email and Push. The remaining rows above are mounted and reachable but are not yet described in that spec, so treat the table on this page, not the JSON, as the full list.

Everything except the public probes and the sign-in routes needs an authenticated session; unauthenticated calls answer 401, and unknown paths answer 404.

Deployment

  • Node.js service behind a TLS-terminating reverse proxy (Caddy), one origin for UI and API.
  • SQLite database on the clinic's own host; snapshots every six hours, 30 retained.
  • Health probe: point monitoring at /health?deep=1 and alert on anything other than 200.
  • The footer of each page reports the running version. If an area in the table above answers 404, the deployment is older than this page — redeploy from the same build that served it.

Downloads and verification

Installers are on the download page. Once a release publishes its binaries, their SHA-256 digests appear in the checksum table at the bottom of that page, served from /downloads/SHA256SUMS.txt; until then that table is not shown, because a checksum the deployment cannot serve is worse than none.

To check a file you already have, open the verifier: it hashes the file locally with the browser's Web Crypto API and compares it against the published digest, or against one you paste in. The file is never uploaded, and the result is either a match or a mismatch — no partial credit.

The same page also verifies the tamper-evident record chain, which is a separate check from an installer's checksum.
